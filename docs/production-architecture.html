CompUse · architecture

From one operator on one box to a multi-tenant service

Where it stands

Half the production checklist is already built. Naming which half precisely is what stops the rest from being designed against a system that no longer exists.

ConcernStateWhat exists in the code
Artifact & evidence storagebuilt Postgres is primary once COMP_USE_DB_URL is set — artifacts, runs, run_events, run_screenshots. Disk survives as the no-DB fallback.
Per-run isolationbuilt One docker run --rm container per run: headed Chromium under Xvfb, driven over CDP, torn down by _browser_session's finally.
Live view & handoverbuilt noVNC per run, x11vnc deliberately without -viewonly. Takeover pauses at a step boundary; resume hands back to the same session.
Run cancellationbuilt interrupt() raises RunInterrupted at the next boundary; unwinding stops the container. Terminal status interrupted, distinct from error.
Crash recoverypartial abandon_orphaned_runs() sweeps stale running/escalated rows at startup. It fixes the row; a container outliving its process is not reaped.
Run executionpartial A threading.Thread inside the API process. Isolated at the browser, not at the worker — a deploy still kills in-flight runs.
Run registrypartial Runs are durable in Postgres, but RunManager._runs is an in-process dict and holds the only handle to a live run's transport.
Target configurationpartial outcome_library is keyed on target["app"] and resolved live, so several hosts already coexist. The allowlist, credentials and provider config are global.
Tenancyabsent No tenant concept anywhere — no column, no scope, no filter. Every artifact and run is global.
Authenticationabsent Anyone who can reach the port can discover, invoke, approve, and take control of a live browser.
Queue & worker poolabsent The API's shape already fits one — 202 plus a run_id to poll — but nothing consumes a queue.
Observabilityabsent Per-run evidence is excellent. Cross-run metrics, tracing and alerting do not exist.

What none of this touches

DiscoveryAgent, ReplayEngine, Guardrail, SensitiveValueTokenizer, EscalationController and the artifact schema stay as they are. Everything below is topology and state management wrapped around that core. If a proposal here requires editing the replay engine, it is the wrong proposal.

What breaks first

In the order it bites, not the order it appears on an architecture diagram. Two of these are single lines of code today.

#BreakTriggerWhere
1Anyone can drive a bank consoleThe first time it is reachable from another machineno auth anywhere

3Two versions of one capability collideSecond replica, concurrent discoverycli.py — _version_lock
4Model quota is exceeded N×Second worker processllm_client.py — _NVIDIA_RATE_LIMITER
5A deploy kills live browser sessionsFirst deploy during a runthread inside the API process
6One run's memory starves the boxConcurrency, or one bad runsandbox.py — no --memory cap
7Tenant A reads tenant B's evidenceSecond customerno tenant scope on any query
8A chat session vanishes mid-conversationRestart, or a second replicachat/session.py — in memory

Breaks 3 and 4 are the sharp ones

_version_lock is a threading.Lock and _NVIDIA_RATE_LIMITER is a module-level object. Both are correct within one process and silently wrong across two — no error, no warning. The version lock lets two discoveries compute the same next version and one silently clobbers the other; the limiter lets N workers each send the full 40 requests a minute. Neither failure announces itself, which is what makes them worse than the outages above them.

Three planes

The split that makes everything else expressible: what accepts requests, what drives browsers, and what remembers.

The rule that makes the split worth having: control and execution never talk directly. A worker publishes escalation state by writing a row; the API learns about it by reading one. That is what lets either side be restarted, scaled or deployed without the other noticing.

Today's process is all three planes at once, which is why a deploy kills a browser session and why one replica cannot see another's runs. Splitting them is mostly a matter of moving RunManager's dict into Postgres and putting a queue between the 202 and the thread — both of which the API's existing shape already anticipates.

Execution & containers

The container per run already exists. What's missing is everything around its lifecycle.

Limits, which do not exist today

sandbox.py sets --shm-size 1g and no memory cap at all. Measured peaks were 428 MiB for a replay or a short discovery and 1126 MiB for a long one that reloaded pages through retries, with CPU bursting to 380–1070% across cores. So the numbers to enforce are known:

ControlValueWhy this number
--memory1.5 GiBAbove the 1126 MiB worst case observed, below two-per-2GiB-box.
--cpus2.0Chromium startup genuinely wants multiple cores; uncapped it takes every core on the box.
--pids-limit512A fork bomb inside a browser container should not need a host reboot.
Max lifetime15 minThe longest legitimate run measured was 9m21s. Beyond that, something is wrong.
Egress policyallowlistThe container should reach the target host and nothing else — see below.

Egress is the isolation gap that matters

The Guardrail allowlist constrains what the agent navigates to. It does not constrain the browser: a page can load a script from anywhere, and a compromised target could use the container as a foothold. Isolation today is a container boundary with an open network. In production the run container gets a per-target egress allowlist at the network layer, so the guardrail's policy and the network's policy say the same thing — one enforced against the agent's intent, one against the browser's actual sockets.

Reaping, which the current design cannot do

Containers are torn down by a finally in the process that started them. Kill that process and the container survives — live-observed this session: three containers still running 38, 45 and 48 minutes after their runs were gone. A reaper keyed on container labels (run_id, tenant_id, started-at) is the only thing that closes it, because the owning process is precisely what has disappeared.

Warm pools, carefully

Container start is a real cost — spawn() polls for published ports and then for Chromium answering CDP, tens of seconds against a ~7s median replay. A warm pool is the obvious fix and a genuine hazard: a reused browser carries cookies, session state and cached credentials across runs, and the one thing this system must never do is leak one tenant's authenticated session into another's run. If pooled, containers are scoped to a single tenant-and-target pair and never reused across either, which limits the win to bursts of the same capability for the same customer.

State & storage

Postgres already holds the durable objects. Three additions and one correction.

runs — add tenant_id, target_id, worker_id, lease_expires_at
The lease is what makes a run recoverable: a worker holds a time-bounded claim it renews, and a run whose lease expires is re-queued or failed by the reaper rather than sitting at running forever. abandon_orphaned_runs() becomes a lease sweep instead of a startup-only sweep.
artifacts — add tenant_id, target_id to the primary key
Two customers will both want member_balance, against different hosts, with different steps. Version numbering scopes to the tenant.
artifact versioning — replace _version_lock
A threading.Lock becomes a unique constraint plus INSERT … ON CONFLICT, or SELECT … FOR UPDATE on a per-capability row. The race the lock was written to prevent is real; the lock's scope is one process.
run_screenshots — move bytes to object storage
Storing PNG bytes in Postgres was the right call at this volume and the wrong one at production scale. Rows keep the metadata and a key; the bytes move to S3-equivalent with a lifecycle policy.
Redis — chat sessions, catalog cache, quota tokens
Chat sessions are in-memory today, so a restart loses a conversation and a second replica cannot see it. The catalog does an approved-version scan per call, invalidated on approve/reject/retire. Quota tokens are covered below.
Queue — jobs carry tenant_id and target_id
Routing, per-tenant concurrency caps and fair scheduling all fall out of having those two fields on the job rather than looking them up later.

Escalation crossing the plane boundary needs no pub/sub. A worker writes the InterventionRequest to the run's row; the API reads it when polled. Escalations are rare and already polled by the dashboard on a 1.5-second timer, so a dedicated bus would be infrastructure bought for nothing.

Many users

Tenancy is the axis with the least existing support — no column, no scope, no filter — and the one where a mistake is a breach rather than an outage.

Two layers, not one

Tenant is the isolation boundary: a customer institution. Artifacts, runs, evidence, credentials and target configuration all scope to it, and nothing crosses. User is the identity within a tenant, and carries the role. Both belong on the job, the run row and the container label, so a query, a schedule and a docker ps all answer the same question the same way.

RoleMay doWhy the line sits here
Caller (agent)Invoke approved capabilitiesThe unattended path. Cannot record, cannot approve, cannot see another tenant.
Operator+ discover, take control, interruptTaking control of a live authenticated banking session is an operator action, not a caller one.
Reviewer+ approve, reject, retireApproval is the gate that stops an unreviewed recording becoming what unattended invoke picks up. Separating it from discovery is the whole point.
Admin+ manage targets, credentials, membersCredential and target configuration is a blast-radius change, not a daily one.

Discovery is an unusually privileged action

A discovery run gives an LLM a live authenticated session on a financial console and lets it decide what to click. The approval gate covers what gets replayed, not what discovery does while recording. Per-tenant discovery quotas, an operator-only role, and an audit trail per run are the compensating controls — and the fact that discovery already refuses to record fault pages, escalates on risky steps and can be interrupted mid-run is why this is defensible at all.

Every query gets a tenant predicate, enforced at a layer no route can forget — Postgres row-level security keyed on a session variable the request handler sets, rather than a WHERE tenant_id = … that a future endpoint omits. A tenant-scoped concurrency cap on the queue keeps one customer's burst from starving another's, and a per-tenant container label makes the boundary visible to the reaper and to anyone debugging the host.

Many target sites

The axis the system is already closest to supporting — and where the remaining work is mostly moving constants into rows.

The precedent is outcome_library.py: a registry keyed on target["app"], resolved live at replay rather than snapshotted into artifacts, returning an empty list for an unrecognised host. Several targets already coexist. The generalisation is to make that shape the norm for everything else that is currently global.

The session model is the real unfinished work

Every capability today re-runs sign-on inside itself, which is why every artifact carries operator_id, password and branch. It also means a session timeout mid-run is classified correctly as recoverable and then cannot be acted on, because OutcomePattern.recovery_action is a single UI step and re-authenticating is a whole flow. Sessions as typed outputs consumed as typed inputs fixes the duplication, the credential spread, and mid-run re-auth in one change — and it is a schema change, so it is the one item here that touches the core.

Many surfaces

The abstraction exists and has never been tested by a second implementation, which is the honest description of every interface in that position.

Surface is already the seam: observe() returns an accessibility tree, act() performs one ActionType, check_checkpoint() answers whether a state holds. Both engines depend on the interface, and _derive_success_checkpoint() was deliberately rewritten to go through Surface.get_heading_text() rather than reach into a Playwright page, precisely so a non-Playwright surface stays possible.

Surfaceobserve()What genuinely differs
Web (built)Playwright aria_snapshot + form-field hints—
DesktopUIA / AX / AT-SPI treeLocators become window-and-control paths. No URL, so URL_MATCHES checkpoints have no meaning and the allowlist needs a different unit — an application identity rather than a prefix.
Terminal (3270/5250)Screen buffer as a field gridGenuinely closer to the artifact model than the web is: fields are addressed by row and column, and a screen is identified by its own text. Risk classification loses every heuristic keyed on control names.

Two things must change before a second surface is real, and both are cheap now and expensive later. ActionType and LocatorStrategy are web-shaped enums; a desktop surface needs its own strategies without web strategies leaking into its artifacts. And Guardrail's risk classification reads control names, which assumes a naming convention a terminal screen does not have — risk rules become per-surface, resolved the same way outcome patterns already are.

Human-in-the-loop, at scale

One operator watching one noVNC tab is a solved problem. Twenty operators and two hundred concurrent runs is a different one.

Today the noVNC URL is a 127.0.0.1 port published by the container, handed to the dashboard, and reachable by anyone who can reach it. In production that becomes a session broker: an escalated run mints a short-lived, single-use ticket scoped to one run, one tenant and one operator; the gateway proxies the connection and logs who connected, when, and for how long. Nothing else changes — the container still serves noVNC, x11vnc still runs without -viewonly, and the EscalationController state machine underneath is untouched.

Escalations also need routing rather than a dashboard someone happens to be looking at: a queue per tenant, an assignment, a timeout, and an escalation-of-the-escalation when nobody claims one. The mechanism already exists for the timeout case — cancel() force-unwinds an abandoned escalation so the run reports a failure instead of holding a browser open forever — but nothing decides when to call it. An unclaimed-escalation SLA is what turns that from a manual escape hatch into a policy.

Model quota across workers

A small component with an outsized failure mode, because it fails silently.

The limiter is a sliding-window log, thread-safe, shared process-wide, correct for one process and wrong for two: each worker independently paces to 40 requests a minute, so N workers send 40N. The quota belongs to the API key, so the counter has to live where the key does — a Redis-backed sliding window keyed on the provider credential, with the same "a slot per HTTP attempt, retries included" rule the in-process version already gets right.

Worth keeping the reason for pacing at all, because it is not politeness: a 429 burns the retry budget, then fails the call over to the fallback provider, spending a free tier capped at 50 requests a day across the whole account. A burst today exhausts tomorrow's fallback. With per-tenant quotas layered on top, the same mechanism also stops one customer's discovery spree from consuming another's capacity — the token bucket is per credential, the fairness cap is per tenant.

Data & secrets

Redaction has a known gap on the live target

The patterns cover the mock bank's ID shapes — ACC-, SUB-, TXN-, CONF-, 9–12 digit numbers, dollar amounts. MERIDIAN's member numbers and share ids such as 103001-MMKT-11 match none of them and are not redacted today. The fix is one regex, because both the LLM-facing tokenizer and the output redaction read the same list — but per-target pattern sets are the production shape, since a pattern list that is a union of every customer's ID formats over-redacts everyone's evidence.

The vision channel stays an exposure

Tokenization is regex over text. The drift-diagnosis path sends a raw screenshot to a vision model, and pixels cannot be tokenized. This is documented rather than solved; at production scale the answer is a per-tenant policy that either disables the vision fallback or requires a self-hosted model for it.

Retention and secrets

Evidence is the audit trail and also a pile of screenshots of a financial console: it needs a retention policy per tenant, deletion on request, and encryption at rest — none of which exist. Provider keys and target credentials move from .env to a secrets manager, injected per run rather than mounted into a long-lived process, so a credential's blast radius is one container's lifetime.

The distinction that matters for alerting is one the system already models correctly and no dashboard yet reads: a business outcome is not a failure. A capability reporting "insufficient funds" worked perfectly. Alerting on hard_failure and on classification drift — a capability whose business-outcome rate suddenly moves — is the signal that the target changed under you. Alerting on non-success would page someone every time a member number was wrong.

Rollout order

Ordered by what is unsafe or silently wrong first, not by architectural tidiness. Each phase is shippable alone.

Phase 1

Stop the silent wrongness

Auth and roles on the API. Move _version_lock to a database constraint and the rate limiter to Redis. Container memory, CPU, pid and lifetime caps. A reaper keyed on labels.

All of it is small, none of it needs a topology change, and every item is either a security hole or a bug that produces no error message. Single-box deployment still works at the end of this phase.

Phase 2

Split the planes

Queue between the 202 and the work. Workers as their own processes, owning container lifecycle. Run state and leases in Postgres; chat sessions in Redis; screenshots to object storage.

This is what buys deploys that do not kill runs, and replicas that agree. The API's shape does not change — it already returns a run_id to poll.

Phase 3

Tenancy end to end

tenant_id on every row, job and container label, enforced by row-level security rather than by remembering a predicate. Per-tenant targets, credentials, allowlists, redaction patterns and concurrency caps. The session broker for scoped noVNC access.

Deliberately after the split: retrofitting tenancy onto a single-process design means doing it twice.

Phase 4

Sessions, then a second surface

The session model — typed session outputs consumed as typed inputs — which removes the credential spread across every artifact and finally makes mid-run re-authentication expressible. Then, and only with a real second target demanding it, a second Surface.

Last because it is the only work here that touches the artifact schema, and schema changes are cheapest once the storage and tenancy shapes have stopped moving.

What not to build

Rejections are part of a design. Each of these is a plausible next component that would be a mistake to add.

A pub/sub bus for escalations
Escalations are rare and the dashboard already polls. A row in Postgres carries the state; a bus would be infrastructure bought to avoid a query.
Kubernetes-per-run, or Firecracker microVMs
A container per run already gives the isolation boundary that matters. MicroVMs buy protection against container escape — real, but a smaller risk than the open network egress the containers have today. Fix egress first; revisit if the threat model changes.
A general capability router
The caller names the capability. Inferring which one to run from a fuzzy goal is the upstream product's job, and building it here would put an LLM back in the invoke path — the exact property the whole design exists to avoid.
Cross-tenant artifact sharing or canonicalization
Tempting because two banks running the same core look similar. But an artifact is a recording of one host's DOM, and "these two targets are the same underneath" is a claim no evidence here supports.
Warm container pools shared across tenants
The saving is tens of seconds. The risk is one tenant's authenticated banking session leaking into another's run. Pool within a tenant-and-target pair or not at all.
